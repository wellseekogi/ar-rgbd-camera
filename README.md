# AR Floor Is Lava · 실시간 깊이 서버

이 문서는 `cpu` 브랜치 기준입니다. GPU가 설치돼 있어도 기본 실행은 CPU StereoSGBM이며 CUDA 패키지를 기본 설치하지 않습니다. GPU 기본 버전은 `gpu` 브랜치, 자동 선택 공통 버전은 `main` 브랜치에서 관리합니다. `run_ui.py`와 `run_api.py` 모두 이 기본값을 따릅니다.

핸드폰의 웹 카메라 영상 두 개를 노트북으로 보내고, 왼쪽 카메라 영상에 정렬된 **픽셀별 깊이맵**을 반환하는 프로토타입입니다. 깊이는 사람 검출 성공 여부와 무관하게 계산합니다.

## 실행

**`start.cmd`를 더블클릭하면 됩니다.** 필요한 환경이 없으면 설치하고, 모델·인증서를 준비한 뒤 서버가 응답하면 웹 화면을 자동으로 엽니다. 노트북 화면은 자동 로그인되고, 화면 맨 위에 카메라별 QR 2개가 자동 표시됩니다. 서버 창은 켜 두세요. 종료하려면 창에서 `Ctrl+C`를 누릅니다. 최초 HTTPS 인증서 신뢰 등록과 실물 카메라 보정은 아래 절차가 필요합니다.

Windows, Python 3.13에서 CPU만으로도 실행할 수 있습니다. 기본 설치에는 CUDA/cuDNN 패키지가 필요하지 않습니다. CPU는 OpenCV StereoSGBM, CUDA가 준비된 GPU는 C-Fast-FoundationStereo를 사용합니다. 두 방식의 정확도가 같다는 뜻은 아니며 CPU에서는 무늬가 적거나 반사되는 영역의 깊이가 비어 있을 수 있습니다.

```powershell
cd C:\증강현실
.\setup.ps1
.\start.ps1
```

IP를 직접 지정하려면 `./setup.ps1 -LaptopIp 192.168.0.10`처럼 실행합니다. IP가 바뀌면 다시 실행해 서버 인증서의 IP 목록을 갱신합니다. 기존 로컬 CA는 유지합니다.

1. `start.cmd` 실행 후 노트북의 ‘핸드폰 연결하기’를 누릅니다. 노트북은 접속 키를 직접 입력하지 않고 자동 로그인됩니다.
2. 왼쪽 폰은 카메라 1 QR, 오른쪽 폰은 카메라 2 QR을 스캔한 뒤 ‘연결하기’를 누릅니다. 키·카메라 번호는 자동 입력되고 URL의 키는 즉시 주소창에서 제거됩니다. QR에는 접속 권한이 있으므로 팀 안에서만 공유합니다. 수동 접속 시에는 `https://노트북IP:8443`과 서버 창의 접속 키를 사용합니다.
3. 핸드폰 카메라를 쓰려면 **신뢰된 HTTPS**가 필요합니다. `certs/lava-local-ca.crt` 공개 인증서만 각 기기에 전달해 OS의 인증서 신뢰 설정에 등록합니다. 노트북 브라우저에도 등록합니다. `ca-key.pem`, `server-key.pem`은 전달하지 않습니다. 인증서 경고를 무시하는 것만으로 카메라 사용이 보장되지는 않습니다.
4. 접속되지 않으면 Windows 방화벽의 Python/8443 접근과 공유기의 기기 간 통신 제한을 확인합니다. 기본 웹 화면은 **HTTPS/WSS, TCP 8443 한 포트**로 페이지·영상·상태를 주고받습니다. 학교 Wi-Fi를 그대로 사용할 수 있지만 **기기 간 TCP 통신 자체가 허용돼야 합니다**. 핫스팟은 필수가 아닙니다. SSL/TLS는 암호화이며 기기 간 차단을 우회하지 않습니다. 별도 WebRTC API는 유지하지만 기본 화면은 UDP를 사용하지 않습니다.
5. 각 폰에서 자동 보정 안내를 따라갑니다. 보정 후 빈 배경을 저장하면 추적이 시작됩니다. 사람이 없어도 깊이맵이 나와야 하며, 게임 시작에는 양발 추적이 추가로 필요합니다.

## 카메라 배치와 보정

### UI 확인용과 연결용 실행 파일

저장소: [wellseekogi/ar-rgbd-camera](https://github.com/wellseekogi/ar-rgbd-camera) (공개).

환경 준비 후 프로젝트 루트에서 둘 중 **하나만** 실행합니다. 같은 8443 포트를 사용하므로 동시에 실행하지 않습니다.

```powershell
# UI 확인용: 카메라 1·2 영상, 깊이 색상, REST 요청·응답 로그. 준비되면 브라우저를 엽니다.
.venv/Scripts/python.exe run_ui.py

# 연결용: 브라우저를 열지 않고 같은 카메라 수신·보정·RGB-D REST 서버를 실행합니다.
.venv/Scripts/python.exe run_api.py
```

### CPU / GPU 선택

이 브랜치의 기본값은 `cpu`입니다. CPU 경로에는 ONNX 모델이나 ONNX Runtime 패키지가 필요하지 않습니다. 그래픽카드가 없는 PC에서는 기존처럼 `start.cmd`를 실행하면 됩니다. 명시적으로 `--depth-device auto`를 지정할 때만 CUDA 우선·CPU 대체 실행을 사용합니다.

```powershell
# GPU가 있는 PC에서도 CPU로 실행
.venv/Scripts/python.exe run_ui.py --depth-device cpu
.venv/Scripts/python.exe run_api.py --depth-device cpu

# NVIDIA GPU 기능 설치 후 강제로 GPU 실행, CUDA 준비 실패 시 오류 표시
.\setup.ps1 -UseCuda
.venv/Scripts/python.exe run_ui.py --depth-device cuda
```

실행 명령은 둘 중 하나씩 사용합니다. `LAVA_DEPTH_DEVICE=cpu` 환경 변수로도 고정할 수 있습니다. GPU 패키지는 `requirements-gpu.txt`에 분리했으며, `requirements-lock.txt`는 기존 CUDA 측정 환경의 참고 스냅샷이므로 CPU 설치에는 사용하지 않습니다. 새 CPU 설치는 `requirements.txt`를 사용합니다. GPU 패키지가 이미 설치된 환경을 CPU 모드로 실행할 때 해당 패키지를 삭제할 필요는 없습니다.

화면 상태와 REST 응답의 `depth_backend`, `depth_device`에서 실제 계산 방식을 확인할 수 있습니다. RGB·0~1 float32 Z·유효 마스크·선택적 사람 마스크의 형식, 카메라 보정 필요 조건, 350ms 만료 기준은 그대로입니다. CPU의 0~96픽셀 미만 시차 탐색 범위 밖이거나 대응점을 찾지 못한 깊이는 무효로 반환합니다. 근거리·반사·무늬 없는 표면의 정확도는 실제 장비에서 확인해야 합니다.

C-Fast-FoundationStereo 자체도 CPU에서 실행해 봤지만 320×192 단일 추론이 약 1974.3ms로, 현재 350ms 기준을 넘었습니다. 그래서 실제 CPU 서비스의 기본 계산에는 그 모델 대신 빠른 StereoSGBM을 사용합니다. 단순히 CUDA를 CPU로 바꾼 동일 모델·동일 정확도 경로가 아닙니다.

두 파일은 공통 서버와 모델을 사용하므로 **각각 독립 실행 가능한 단일 파일 프로그램은 아닙니다.** 저장소 전체와 모델·환경 준비가 필요합니다. API 모드에서도 폰의 카메라 연결·보정 페이지는 필요하므로 해당 기능을 유지합니다. 외부 프로그램은 `GET /api/rgbd/frame`을 호출하며, 단건 수신 예제는 `scripts/fetch_rgbd.py`입니다.

UI에서는 카메라 1·2 영상과 깊이맵을 나란히 표시합니다. 두 영상이 들어오면 QR 영역은 자동으로 접히며 다시 펼쳐 새 기기를 연결할 수 있습니다. 실제 REST 호출은 응답 후 1초 간격으로 수행하며 **HTTP 상태, 요청·응답 시간, 응답 바이트 크기, 프레임 ID와 JSON 필드**를 펼쳐 볼 수 있습니다. 최근 20개 기록을 유지하고 큰 Base64는 표시만 축약합니다. API가 409를 반환하면 보정·연결·GPU 지연 안내도 그대로 표시합니다. 로그만 일시정지·비우기 할 수 있고 영상은 계속 표시합니다.

### 카메라 배치와 보정 순서

- 좌우 두 폰은 같은 바닥과 플레이어를 볼 수 있게 **단단히 고정**합니다. 일반 후면 렌즈를 권장하며, 줌·렌즈·위치를 바꾸면 다시 보정합니다. 정해진 최적 카메라 간격은 실측으로 결정해야 합니다. 코드의 0.05~3m 검사는 사용 범위 제한이며 정확도 보증이 아닙니다.
- 화면에서 기준판 PNG를 받습니다. **전체 200×280mm, 한 칸 40mm**로 인쇄해 실제 크기를 자로 확인합니다. 출력물에 맞춰 실제 치수를 바꾸려면 `ar_lava/calibration.py`의 `SQUARE_M`, `MARKER_M`을 함께 바꿉니다.
- **움직이며 자동 보정:** QR 연결 후 새 영상이 들어오는 카메라부터 바로 안내합니다. 두 카메라는 각각 안내에 따라 보정합니다. 폰과 노트북에 진행 링, 실시간 기준판 테두리, 요구사항 체크리스트가 표시됩니다.
- 기준판 전체를 보면서 카메라를 천천히 움직입니다. **가운데·좌·우·위·아래, 가까이·멀리, 15도 이상 돌리기**가 실제 사진에서 확인되면 체크됩니다. 이동 후 잠시 멈추면 선명하고 서로 다른 사진을 자동 수집합니다. **12장 이상과 모든 촬영 조건**을 만족하면 렌즈 보정을 계산하며, 허용 RMS는 **1.5px 이하**입니다. 40장으로도 보정하지 못하면 사진 초기화 후 다시 시작하도록 안내합니다.
- 렌즈 보정 뒤에는 기준판을 바닥에 놓고 **모든 카메라를 최종 위치에 단단히 고정**합니다. 모든 폰이 **같은 판·같은 위치·방향**을 봐야 합니다. 각 폰의 `카메라 고정 완료 · 바닥 맞추기`를 누르면 기준판 인식과 안정된 영상을 확인한 뒤 위치를 자동 계산합니다. 바닥 원점은 기준판 좌표계입니다.
- **연결된 모든 카메라의 바닥 보정이 끝날 때까지 기준판을 움직이지 마세요.** 이후 사람이 화면에서 나간 뒤 각 폰의 `사람 없는 빈 배경 저장 · 깊이 시작`을 누릅니다. 사람이 없는지는 사용자가 확인하며 자동 판정하지 않습니다. 깊이는 **카메라 1·2**로 계산합니다.
- 기존 사진 추가·내부/외부 보정·배경·추적 버튼은 노트북의 `수동 보정 · 다시 보정` 안에 있습니다. 수동 버튼을 사용하면 자동 사진 수집을 멈추며 `자동 안내 켜기`로 돌아갈 수 있습니다. 폰에서도 `이동·렌즈 변경 후 다시 보정`으로 처음부터 시작할 수 있습니다.
- 내부 보정은 프로필별로 파일에 저장합니다. **재접속·서버 재시작 시 외부 위치 보정은 다시 해야 합니다.** 카메라 움직임을 자동 검출한다고 가정하지 않습니다.

### 거리별 색상 깊이맵

노트북과 카메라 1의 폰에서 `거리별 색상`, `원본에 색상 겹치기`, `원본 영상`을 선택할 수 있습니다. 색상과 원본은 **같은 프레임·같은 원본 좌측 카메라 좌표**를 사용합니다.

- **빨강 0.1m 초과 → 노랑 2m → 초록 4m → 파랑 8m 이상**의 고정 범례입니다. **8~15m는 같은 파랑**이며 실제 깊이 데이터는 유지합니다. 무효 픽셀은 검정입니다.
- 중앙 십자선의 실제 깊이를 **미터**로 표시하고, 측정 가능한 픽셀 비율과 모델 처리 시간을 함께 보여줍니다. 측정 비율은 정확도 점수가 아닙니다. 거리는 카메라 1의 **광축 Z 방향 깊이**입니다.
- 깊이 계산 준비 조건을 체크리스트로 보여주며, 연결이 끊기거나 새 깊이 영상이 **1.5초** 동안 없으면 이전 표시를 지웁니다. 실시간 서버는 기존 **350ms** 결과 유효시간을 유지합니다.

## 반환값

정합 담당자의 **REST + 0~1 float32** 요구에는 `GET /api/rgbd/frame`을 사용합니다. 카메라 1·2로 깊이를 계산하고 **카메라 1의 원본 JPEG + 같은 픽셀·시점의 정규화 Z-depth + 유효 마스크 + 보정값 + 발 추적값**을 JSON 한 응답으로 반환합니다. 여러 카메라 영상을 합성하지 않습니다.

사람이 한 명 확인되면 기존 MediaPipe 포즈 추론의 사람 영역 확률을 **선택적 `segmentation` PNG8**로 함께 반환합니다. RGB와 동일한 크기·프레임 ID이며, 마스크를 얻지 못하면 `available=false`입니다. 필수 깊이 유효 마스크와 구별합니다. 현재 기본 모델은 MediaPipe Pose Landmarker Lite이며 SAM이나 별도 RVM 추론을 추가하지 않았습니다.

깊이는 Base64로 감싼 little-endian float32 `[height,width]`입니다. **고정 범위 0.1~15m**, 복원식은 `Z_m = 0.1 + d * 14.9`이며 무효 픽셀은 별도 uint8 마스크로 구분합니다. 프레임 ID로 중복을 구별하며, 보정 변경·연결 끊김·350ms 만료 시 409입니다. 수신 예제는 `scripts/fetch_rgbd.py`, 전체 규약은 `docs/TEAM_API.md`에 있습니다. 기존 미터 단위 NPZ/NPY API도 유지합니다.

핵심은 `depth_m[y,x]`입니다. **왼쪽 원본 카메라의 광축 Z 방향 거리, 미터 단위 float32**이며 유클리드 직선거리가 아닙니다. 가상 장면의 깊이도 동일 카메라 좌표·단위로 변환해 비교해야 합니다.

- 깊이 추론: 기본 **320×192**. 반환 깊이는 왼쪽 입력 영상 크기로 좌표 정렬하지만, 이것이 고해상도 깊이 복원을 뜻하지는 않습니다.
- 두 카메라의 공통 시야 바깥, 대응 실패, 범위 밖 깊이는 **NaN**입니다. 유효 범위는 **0.1m 초과~15m 이하**입니다. 모델은 픽셀별 신뢰도 출력을 제공하지 않으므로 유효 마스크를 정확도 보증으로 해석하면 안 됩니다.
- 실시간 WebSocket: `/ws`에 `{"role":"depth","token":"접속키"}`를 첫 메시지로 전송합니다. **깊이 PNG16 + 동일 시점 기준 JPEG + 시각화 JPEG + 메타데이터**를 받습니다. PNG 깊이는 **1mm 단위, 0은 무효**입니다.
- 단건 묶음: `GET /api/depth/frame.npz`, 헤더 `X-Session-Key: 접속키`. float32 깊이·기준 JPEG·보정값을 같은 결과로 받습니다. 개별 요청 사이에 프레임이 바뀔 수 있으므로 통합 NPZ나 WebSocket 패킷을 사용합니다.
- 자세한 바이트 규약과 렌더링 예시는 `docs/TEAM_API.md`를 참고합니다.

## 지연과 검증 범위

**HTTPS/WSS로 압축 JPEG 영상을 보내고**, 폰마다 응답을 기다리는 프레임은 한 개로 제한합니다. 최대 촬영 전송 주기는 15FPS이며 서버에는 카메라별 최신 대기 프레임 한 개만 유지합니다. WebRTC보다 영상 압축 효율이 낮을 수 있고, 실제 전송량·전체 지연은 장비에서 측정해야 합니다. 깊이 추론도 한 작업만 실행하고 다음 작업은 최신 좌우 영상으로 교체합니다. 모델은 서버 시작 때 한 번 로드합니다. 느린 구독자는 과거 결과를 쌓지 않습니다.

초기 정책값은 좌우 시각 차이 **40ms 이하**, 서버가 받는 영상 나이 **350ms 이하**, 시계 왕복 **100ms 이하**입니다. 350ms보다 오래된 깊이는 게임 판정·API에서 사용하지 않습니다. 이 값들은 실제 장비에 맞춰 검증·조정해야 합니다.

기본 WSS 경로는 브라우저가 캔버스에 그린 시각을 프레임 번호·카메라 프로필과 함께 JSON 헤더에 넣어 보냅니다. 동일 소켓의 ping/pong으로 단조 시계를 맞춥니다. 별도 WebRTC API는 영상 하단 시간 표식을 사용합니다. **센서의 실제 노출 시각을 측정하거나 두 폰을 하드웨어 동기화하는 기능은 아닙니다.** 롤링 셔터·기기별 영상 지연 때문에 움직이는 사람의 경계에 깊이 오차가 날 수 있습니다. 고속 동작의 오차가 크면 하드웨어 동기화 스테레오 카메라가 필요할 수 있습니다.

RTX 3050 Ti 4GB에서 NVIDIA 공식 샘플, FP32 ONNX/CUDA, 준비 추론 1회 후 5회 측정:

| 입력 | 추론 중앙값 | 추론 p95 |
|---|---:|---:|
| 320×192 | 141.4ms | 141.6ms |
| 640×384 | 511.4ms | 513.3ms |

**네트워크·보정·결과 압축·합성을 제외한 모델 단독 측정**입니다. 30FPS나 두 핸드폰의 실제 전체 왕복 지연을 보장하지 않습니다. 실제 폰의 깊이 정확도, 가려짐 경계, 캘리브레이션·동기화는 현장 검증이 남아 있습니다. FP16 단순 변환은 그래프 타입 오류가 발생해 적용하지 않았으며, TensorRT 최적화는 미적용입니다.

## 구성

- 웹: JavaScript, Canvas, HTTPS/WSS. WebRTC API는 선택적으로 유지합니다. 빌드·외부 CDN 없이 서버에서 정적 파일을 제공합니다.
- 서버: Python, FastAPI, aiortc, OpenCV. `calibration.py`는 카메라 보정, `rtc.py`는 전송, `stereo.py`는 정렬·시차·깊이 변환, `render.py`는 합성입니다.
- 깊이 모델: NVIDIA **C-Fast-FoundationStereo** 공식 ONNX. 원본 SHA256를 설치 시 확인합니다. 모델 출처·약관 링크는 `models/PROVENANCE.json`에 기록합니다.
- 게임 보조: MediaPipe Pose Landmarker의 관절·사람 마스크, `game.py`의 경고·용암·생명·제한 시간. 깊이맵을 샘플링한 양발 위치로 판정하며, 깊이 서비스와 분리되어 있습니다.
- 카메라 영상은 기본적으로 디스크에 저장하지 않습니다. 보정·접속 키는 `data/`, 인증서는 `certs/`에 저장하며 배포 ZIP에서 제외합니다.

## 개발 검증

```powershell
.\.venv\Scripts\python -m pip install -r requirements-dev.txt
npm ci
.\.venv\Scripts\python -m pytest -q
.\.venv\Scripts\python -m ruff check ar_lava scripts tests
npm run lint
npm run typecheck
npm run test:web
```

연결 표시는 **연결 대기 → 서버 연결됨·영상 확인 중 → 영상 수신 중**으로 구분합니다. 카메라 카드에는 FPS·수신 수·영상 나이를 표시하며 2초 이상 영상이 없으면 ‘영상 끊김’, 폰은 3초 동안 처리 응답이 없으면 경고 후 연결을 종료합니다. ‘서버 연결 확인하기’는 페이지 서버 응답만 검사하므로 실제 영상 수신 확인과 구분해야 합니다.

브라우저 검사는 설치된 Chrome과 가상 카메라 2개를 사용합니다. 실제 폰 검사와 구분해야 합니다. `scripts/benchmark_depth.py`로 좌우 정렬된 이미지 파일을 입력해 GPU 추론 시간을 측정할 수 있습니다.

## 기술 근거

- [NVIDIA Fast-FoundationStereo 공식 구현](https://github.com/NVlabs/Fast-FoundationStereo): 정렬된 좌우 RGB 영상에서 시차를 예측하며 보정값으로 metric depth를 계산합니다. 공식 성능표의 GPU는 RTX 3090입니다.
- [공식 C-Fast-FoundationStereo 모델](https://huggingface.co/nvidia/c-fast-foundationstereo): NVIDIA Open Model Agreement와 모델 카드의 사용 조건을 확인해야 합니다. 모델을 프로젝트 라이선스로 재허가하지 않습니다.
- [공식 single-ONNX 입력 규약](https://github.com/NVlabs/Fast-FoundationStereo/blob/master/scripts/make_single_onnx.py): RGB ImageNet 정규화, `left_image`·`right_image`, 출력 `disparity`.
- [OpenCV 보정·3D 문서](https://docs.opencv.org/4.x/d9/d0c/group__calib3d.html), [aiortc](https://aiortc.readthedocs.io/en/latest/), [MediaPipe Pose](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker?tab=Python), [브라우저 HTTPS 카메라 조건](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia).

폐기한 이전 프로젝트의 명세 폴더 4개와 ZIP 4개는 삭제했습니다. 기존 `.validation`의 공용 검증 라이브러리는 주제 자료가 아니므로 유지했습니다.
