# 변경 내용과 이유

정리일: 2026-11-17

이 프로젝트는 두 핸드폰의 영상을 받아 카메라 1 기준의 RGB와 깊이를 반환하는 서버입니다. 아래는 현재까지 반영한 내용과 그 이유입니다. 실제 사용 순서는 [README](../README.md), 응답 필드와 수신 방법은 [팀 연결 규약](TEAM_API.md), 검사 기록은 [검증 기록](VERIFICATION.md)에 있습니다.

## 1. 카메라는 두 대만 사용

처음에는 세 번째 카메라를 보조 미리보기로 연결할 수 있었지만, 깊이 계산에는 원래 카메라 1·2만 사용했습니다. 세 번째 카메라가 필수인 것처럼 보이는 혼동을 없애기 위해 역할 선택, QR, 보정 패널, 미리보기와 서버 등록에서 제거했습니다. `cam3`로 REST·WebRTC·WebSocket 연결을 시도해도 거부합니다.

카메라 1은 기준 RGB를 제공하고, 카메라 2는 같은 공간을 다른 위치에서 촬영해 깊이 계산을 돕습니다. 두 카메라가 같은 플레이 영역을 충분히 겹쳐 보도록 설치해야 합니다. 현재 로직에는 세 번째 카메라가 필요하지 않습니다.

## 2. 반환 기준을 카메라 1로 고정

여러 카메라 영상을 이어 붙이지 않고 카메라 1의 원본 JPEG와 그 픽셀에 맞춘 깊이를 반환합니다. 정합 담당자가 RGB의 `(u,v)`와 깊이의 `[v,u]`를 같은 위치로 사용할 수 있게 하기 위해서입니다. 카메라 2 영상은 깊이를 계산하는 입력입니다.

원본 RGB에는 렌즈 왜곡이 남아 있으므로 깊이도 원본 영상 좌표에 정렬합니다. 카메라 내부 행렬, 왜곡 계수, 세계 좌표에서 카메라 좌표로 가는 변환도 함께 반환합니다. 가상 카메라와 시점을 맞추는 작업은 이 보정값을 이용해 정합 쪽에서 처리해야 합니다. 이것만으로 자동 전신 모션 캡처나 임의 시점의 사람 재구성이 되는 것은 아닙니다.

## 3. REST 한 응답에 같은 프레임의 데이터를 묶음

`GET /api/rgbd/frame`이 다음 데이터를 반환합니다. 인증 헤더는 `X-Session-Key`입니다.

- `image`: 카메라 1 원본 JPEG.
- `depth`: 같은 크기·같은 좌표의 0~1 정규화 Z 깊이. Base64로 감싼 little-endian float32 바이트입니다.
- `valid_mask`: 깊이를 사용할 수 있는 픽셀은 1, 사용할 수 없는 픽셀은 0인 uint8 배열입니다.
- `segmentation`: 얻을 수 있을 때만 포함되는 사람 영역 확률 마스크입니다.
- `camera`, `tracking`, 프레임 ID와 시각: 보정값, 발 추적값, 프레임 대응에 필요한 정보입니다.

깊이는 프레임마다 다른 범위로 정규화하지 않고 0.1~15m의 고정 범위를 사용합니다. 복원식은 `Z_m = near_m + d * (far_m - near_m)`입니다. 실제 유효 범위는 0.1m 초과~15m 이하이며, 무효 값도 정규화 값 0으로 표현하므로 반드시 `valid_mask`를 함께 읽어야 합니다. Z는 카메라 광축 방향 깊이이고 카메라에서 픽셀까지의 직선 거리는 아닙니다.

요청할 때마다 추론을 다시 시작하지 않고 가장 최근에 계산한 결과를 반환합니다. RGB·깊이·마스크를 한 프레임에 묶어 새 영상과 이전 깊이가 섞이는 문제를 막았습니다. 좌우 촬영 시각 차이는 40ms 이하, 결과 유효시간은 서버 기준 350ms 이하입니다. 준비되지 않았거나 만료·연결 해제·재보정된 결과는 HTTP 409로 알립니다. 네트워크로 전송된 뒤까지 350ms 이내라는 보장은 아닙니다.

웹에서 보여주는 영상과 깊이는 실시간 연결을 사용하고, 외부 정합 프로그램에는 요청받은 REST 규약을 유지했습니다. REST 클라이언트는 응답을 받은 뒤 다음 요청을 보내고, 같은 `frame_id`가 다시 오면 중복 프레임으로 처리하면 됩니다.

## 4. 사람 마스크는 기존 추론 결과를 재사용

MediaPipe Pose Landmarker Lite가 이미 만드는 사람 영역 확률을 재사용합니다. 별도의 무거운 세그멘테이션 모델을 추가하지 않고 현재 환경에서 RGB·깊이와 맞는 사람 마스크를 함께 제공하기 위해서입니다. 최신 모델이라는 이유만으로 SAM 등을 추가하지 않았습니다.

한 사람이 확인되고 유효한 마스크가 있을 때 `segmentation.available=true`와 PNG8 데이터를 반환합니다. 마스크를 얻지 못하면 `available=false`이며, 필수 RGB·깊이 응답은 계속 제공할 수 있습니다. 이 마스크는 사람 영역의 확률이고 광학적으로 정확한 알파 매트나 깊이 유효 마스크가 아닙니다. 현재 3D 추적값도 발 관련 관절·양발 위치이며 전신 추적이나 사람 ID 유지는 제공하지 않습니다.

## 5. 보정 과정을 화면에서 따라가도록 변경

카메라마다 진행 링, 기준판 인식 테두리, 체크리스트와 다음 행동을 표시합니다. 연결 후 영상이 들어오는 카메라부터 안내하며, 두 폰 모두 연결될 때까지 보정 시작을 기다리지는 않습니다.

가운데·좌·우·위·아래 위치, 가까이·멀리, 15도 이상 기울이기 조건을 실제 사진에서 확인합니다. 선명하고 다른 사진이 12장 이상 모이고 모든 촬영 조건을 채우면 렌즈 보정을 계산합니다. 허용 RMS는 1.5px 이하이며, 40장으로도 보정하지 못하면 다시 촬영하도록 안내합니다. 단순히 카메라를 움직였다는 이유로 체크하지 않습니다.

연결 QR과 보정용 출력물은 역할이 다릅니다. QR은 폰을 서버에 연결하는 링크이고, 실제 보정에는 ChArUco 기준판이 필요합니다. 기준판은 전체 200×280mm, 한 칸 40mm로 출력하고 실제 크기를 확인해야 합니다. CPU·GPU 모두 같은 출력물을 사용합니다.

렌즈 보정 후 두 카메라를 최종 위치에 고정하고, 같은 위치·방향의 바닥 기준판을 보고 위치를 맞춥니다. 두 카메라의 바닥 보정이 끝날 때까지 판을 움직이면 안 됩니다. 그다음 사람이 없는 배경을 저장합니다. 빈 배경인지와 최종 고정은 사용자가 확인하며, 카메라 이동을 자동 검출한다고 가정하지 않습니다. 렌즈·줌·위치를 바꾸면 재보정해야 하고, 재접속·서버 재시작 후 외부 위치 보정도 다시 해야 합니다.

## 6. 영상·거리별 색상·REST 로그를 한 화면에 표시

카메라 1·2 영상과 깊이맵을 나란히 표시합니다. 깊이는 빨강에서 노랑 2m, 초록 4m, 파랑 8m 이상으로 바뀝니다. 8~15m는 같은 파랑이고 실제 깊이 값은 유지합니다. 무효 픽셀은 검정으로 표시해 먼 거리와 구분합니다. 원본 위에 색상을 겹쳐 보는 모드, 중앙 Z 수치와 유효 픽셀 비율도 제공합니다. 유효 비율은 정확도 점수가 아닙니다.

REST 로그에서는 실제 `GET /api/rgbd/frame`의 HTTP 상태, 요청 시간과 응답 내용을 확인합니다. 큰 Base64는 앞부분과 길이만 표시해 화면이 데이터를 전부 펼치느라 막히지 않게 했습니다. 화면의 로그 요청은 응답 후 1초 간격이며 영상 수신과는 별개입니다. 로그를 멈춰도 영상은 계속 볼 수 있습니다.

연결 끊김·수신 지연·보정 대기를 상태로 구분하고 이전 영상을 정리합니다. 깊이 화면의 1.5초 표시 만료는 화면 정리 기준이며, 서버의 350ms 결과 유효시간을 늘린 것이 아닙니다. 데스크톱 1440px와 모바일 390px에서 표시와 가로 넘침을 검사했습니다.

## 7. CPU와 GPU 실행을 분리

CPU는 OpenCV StereoSGBM을 사용합니다. CUDA나 ONNX 깊이 모델 없이 실행할 수 있고, 같은 RGB-D 반환 규약을 사용합니다. CUDA 모델을 그대로 CPU로 돌리는 방식은 이 환경의 단독 탐색 측정에서 약 1974.3ms가 걸려 CPU 기본 경로로 사용하지 않았습니다.

GPU는 NVIDIA CUDA와 C-Fast-FoundationStereo ONNX 모델을 사용합니다. 두 방식은 알고리즘이 다르므로 깊이 정확도와 유효 영역도 같다고 보장하지 않습니다. CPU에서는 무늬 없는 곳, 반사면과 가려진 영역의 깊이가 비어 있을 수 있습니다. 두 방식 모두 두 카메라의 보정이 필요합니다.

`main`은 자동 선택, `cpu` 브랜치는 CPU 기본값, `gpu` 브랜치는 CUDA 기본값으로 관리합니다. `auto`는 CUDA 초기화가 실패하면 CPU로 전환하지만, `cuda`로 명시하면 CPU로 전환하지 않고 깊이 준비 오류를 표시합니다. 실제 장치는 상태·깊이 메타데이터·REST 응답에서 확인할 수 있습니다.

실행 파일도 나눴습니다.

- `start_cpu.cmd`: CPU 모드를 명시하고, 필요한 경우 `requirements-cpu.txt`로 환경을 준비합니다. 깊이용 ONNX 모델은 받지 않습니다. 포즈 모델과 HTTPS 인증서는 필요합니다.
- `start_gpu.cmd`: CUDA 모드를 명시하고, 필요한 경우 `requirements-gpu.txt`로 환경을 준비합니다. GPU 모델도 준비합니다. NVIDIA GPU·호환 드라이버와 정상적인 CUDA 초기화가 필요합니다.
- `start.cmd`: 기존 실행 파일입니다. 브랜치 기본값 또는 `LAVA_DEPTH_DEVICE` 설정을 따릅니다.
- `run_ui.py`: UI 확인용으로 브라우저를 엽니다. `run_api.py`: 브라우저 자동 실행 없이 카메라 수신·REST 서버를 실행합니다. 장치를 명시하려면 `--depth-device cpu` 또는 `--depth-device cuda`를 붙입니다.

두 CMD는 공통 `start.cmd`의 환경 검사·모델 준비·서버 시작 경로를 재사용합니다. 실행한 폴더 안의 코드를 사용하며 Git 브랜치를 자동으로 바꾸거나 업데이트하지는 않습니다. 같은 포트와 작업 폴더를 사용하므로 CPU·GPU 서버는 하나씩 실행합니다. 두 CMD만 따로 복사해서 실행하는 방식은 아닙니다.

## 8. 반복 후처리를 보정별로 캐시

SGBM 뒤에서 원본 해상도의 모든 픽셀을 매번 역왜곡하고 전체 XYZ를 계산하던 부분을 줄였습니다. 원본 픽셀의 정렬 좌표와 Z 계산 계수, 바닥 평면의 깊이는 보정이 같으면 바뀌지 않으므로 한 번 계산해 재사용합니다. 매 프레임은 시차를 remap하고 필요한 Z만 복원합니다.

보정 generation이나 보정 객체가 바뀌면 캐시를 다시 만듭니다. 초기 캐시 생성도 작업 스레드에서 실행해 서버 이벤트 루프를 막지 않게 했습니다. 입력 해상도·320×192 깊이 계산 해상도·SGBM 설정·깊이 범위·반환 규약은 변경하지 않았습니다.

이 노트북의 합성 데이터에서 측정한 CPU `compute()` 중앙값은 다음과 같습니다. 정렬·색상화·JPEG/PNG 인코딩·게임 합성을 포함하며, 최초 캐시 생성·MediaPipe·REST 직렬화·네트워크는 제외합니다. 준비 실행 후 5회 중앙값입니다.

| 입력/반환 영상 크기 | 변경 전 | 변경 후 |
|---|---|---|
| 640×480 | 106.595ms | 40.787ms |
| 1280×720 | 349.522ms | 192.863ms |

최초 캐시 생성에는 같은 실행에서 각각 약 56.5ms, 221.1ms가 들었습니다. 1280×720에서는 캐시 배열 약 28.1MiB가 추가됩니다. 반복 계산을 줄이는 대신 처음 준비하는 시간과 메모리를 쓰는 변경입니다. 실제 폰의 FPS나 왕복 지연을 뜻하지 않습니다.

회전·왜곡 유무와 두 입력 크기에서 이전 계산과 비교해 무효 깊이 마스크 일치, 깊이 차이 0.000002m 이내, 합성 영상 픽셀 일치를 검사했습니다. 재보정 후 캐시가 교체되고 다음 프레임에서 역왜곡을 반복하지 않는지도 확인했습니다.

색상 LUT는 기존 색을 근사하므로 적용하지 않았습니다. 전역 gzip은 이미 압축된 JPEG·PNG에도 CPU 비용을 쓸 수 있어 넣지 않았습니다. 합성 영상은 WebRTC에서 사용하고 REST도 결과를 요구할 수 있으므로 시청자가 없다는 이유로 생성을 생략하지 않았습니다. 출력 해상도와 SGBM 해상도 조정은 별도 협의 대상으로 남겼습니다.

## 9. 연결과 배포

기본 웹 연결은 HTTPS/WSS와 TCP 8443 한 포트를 사용합니다. 폰 카메라 권한을 쓰려면 로컬 CA 인증서를 각 기기에서 신뢰하도록 등록해야 합니다. 같은 네트워크에서도 공유기가 기기 간 연결을 막으면 접속할 수 있습니다. 기본 웹 전송은 UDP가 필요하지 않습니다.

QR에 접속 권한을 넣어 키와 카메라 번호를 반복 입력하지 않게 했습니다. 키는 URL fragment에 넣고 접속 후 주소창에서 제거합니다. QR은 팀 안에서 공유하고, 인증서 개인키와 세션 키를 저장소에 올리지 않습니다. 소스 ZIP에도 가상 환경, 모델 가중치, 인증서와 촬영 데이터는 넣지 않습니다.

## 10. 확인 범위와 남은 일

후처리 캐시 반영 시점에는 각 브랜치의 Python 검사 68개와 Ruff·웹 lint·타입 검사를 통과했습니다. 공식 좌우 샘플을 실제 CPU·CUDA로 계산해 HTTP NPZ, RGB-D JSON 200과 WebSocket PNG16 반환도 확인했습니다. 이는 실제 폰 캘리브레이션의 정확도를 확인한 결과는 아닙니다.

두 카메라 동시 수신·독립 보정 안내·QR 두 개·깊이 색상·REST 로그의 브라우저 검사도 수행했습니다. 다만 전체 브라우저 검사에는 촬영 종료 후 가상 카메라 재연결 실패 1건이 남아 있습니다. UI의 성공 응답 fixture와 실제 깊이 계산 검사를 구분해 기록했습니다.

남은 확인은 실제 두 폰과 출력 기준판으로 보정 정확도, 조명·노출 차이, 가림 영역, 플레이 중 전체 지연과 REST 전송량을 확인하는 일입니다. 브라우저의 촬영 시각 추정은 하드웨어 동기화를 대신하지 않습니다. 실측 결과를 보고 해상도·요청 주기·압축 여부를 조율해야 합니다.
